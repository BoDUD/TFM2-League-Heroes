# 性能：英雄多了以后加载慢、比赛卡顿（2026-10-02）

用户反馈："这游戏 mod 英雄多了后加载卡顿变慢"。这份文档记录查到的原因、实测数字、已经做的改动和还能做的事。数字都是实测的；只靠推断的地方会标出来。

## 结论

| 现象 | 原因 | 改法 | 效果 |
|---|---|---|---|
| 启动慢 | 游戏启动时把 mod 里除背景音乐外的每个文件整个读进内存。装好的 league 是 78 MB、1560 个文件，其中 WAV 音效 66 MB。这台电脑的游戏装在机械硬盘上，冷启动光读这些文件就要 16 秒 | 安装和上传都用 `tools/package_mod.py` 打包：音效转 MP3、图集去重重排、JSON 去空白 | 78 MB → 19 MB；机械盘冷读取 16.1 秒 → 4.1 秒 |
| 有剑姬的比赛越打越卡 | 剑姬 W 的特效投射物速度只有 100，又追着目标飞，能在场上留好几分钟。剑姬一死，引擎每 tick 都要为每个残留的投射物把死掉的剑姬整个复制一遍（包括 4 个技能的完整效果树） | 改成飞 4500 距离就结束的直线投射物，画面不变（用户已批准） | 15 分钟对局每 tick 的 CPU：一个剑姬 −40%，双方各一个 −59% |
| 比赛里 mod 英雄越多越吃 CPU | 屏幕上正在放的比赛里，引擎每 tick 为每个 mod 英雄把 skill、skill2 两棵效果树各复制一遍再丢掉 | 打包时去掉不起作用的包装，17 个英雄的效果树按英雄等价改写（第 8 节，2026-10-18；同种子对局逐 tick 相同） | 10 个联盟英雄的对局每 tick CPU 约是原版英雄的 4 倍；改过的九个英雄同场 −13.7%，全部 skill + skill2 节点 −7.7% |
| 选人、图鉴界面 | 每个英雄的图集都要解码成 RGBA。原来的图集一半是空白 | 打包时去掉重复帧、紧凑重排 | 解码后 103 MB → 52 MB |
| 启动又要一分多钟（2026-10-17，119 个英雄、5282 个文件），创意工坊玩家也一样 | 启动的开销按**文件个数**算：机械盘上每个文件一次寻道，更新后每个新文件被 Defender 扫一次。2088 个音频占四成 | 打包时音频放进 `sound/bgm/`（游戏播放时才打开，启动不读）；`league.dll` 在标题画面出来后把它们预读进系统缓存（第 7 节） | 启动读的文件 5282 → 3194；机械盘文件分散时冷启动 88 → 51 秒，更新后第一次 101 → 62 秒，刚下载完 16.1 → 8.5 秒；比赛里第一次播放不卡 |

## 1. 启动加载

### 引擎怎么读 mod

从 `TeamfightManager2.exe`（0.6.2）的字符串和反汇编看到的：

- mod 文件夹由 engine-core `assets.rs` 的加载器逐个文件读取。只有 `/sound/bgm/` 下的 .wav/.mp3 登记为流式播放，**其余每个文件都在启动时整个读进内存**，包括全部音效。所以音效体积直接等于启动时的读盘量和常驻内存。
- 音频只支持 .mp3 和 .wav。别的格式（.ogg）会提示 `Unsupported audio file "{Path}". Only .mp3 and .wav are supported.`
- 音效第一次播放时，把内存里的字节复制进缓存；每次播放都在音频线程里用 rodio 0.21 + symphonia 0.5.4 边播边解码，不在启动时解码，也不占主线程。
- 原版 498 个音效全是 MP3（大多 192 kbps 立体声，带 LAME 头），所以换成 MP3 走的是引擎本来的路线。
- 日志：即使 `config/game/base.json` 里 `"log": false`，`%APPDATA%\TeamSamoyed\TeamfightManager2\data\log.log` 也会写 `state init done..` 和 `asset loading done!` 两行，时间差就是资源加载用时。

### 这台电脑上的实测

游戏在 D 盘：一块 5900 转的机械硬盘（ST2000DL001），不是固态。

| 测量 | 结果 |
|---|---|
| 绕过 Windows 文件缓存，按目录顺序读完 `mods/league`（相当于冷启动） | 1560 个文件、78.1 MB，**16.1 秒**（4.8 MB/s，平均每个文件 10 ms，主要花在寻道） |
| 其中 WAV | 646 个、65.9 MB，8.7 秒 |
| 其余小文件 | 914 个、12.2 MB，7.4 秒 |
| 7 月 13 日日志里的资源加载（当时启用的是 lol_mod） | 18.2 秒 |
| 今天 10:11（文件还在系统缓存里） | 3.9 秒 |

对比：C 盘的 NVMe 固态上，仓库里的 `league`（76.5 MB、1516 个文件）同样绕过缓存读一遍只要 0.7–0.9 秒。所以"加载慢"主要出在机械硬盘的冷启动上。

另外，文件第一次被打开时 Windows Defender 会扫描它（实时保护开着）：刚写进去的文件第一次读，固态上每个文件 6–11 ms，机械盘上新文件夹第一次读要 22.9 秒；扫描结果有缓存，之后就快了。病毒库更新后会重新扫描，文件越小、越少，这一步越快。

### 打包后

`python tools/package_mod.py`（41 个英雄，main c5a99af + 剑姬修复）：

| 文件 | 打包前 | 打包后 |
|---|---|---|
| 音效 .wav → .mp3 | 64.5 MB | 11.7 MB |
| .data_champion | 6.4 MB | 1.7 MB |
| .png（图集、图标） | 4.6 MB | 4.5 MB |
| 其他 JSON | 1.1 MB | 1.0 MB |
| 合计 | **76.5 MB** | **19.0 MB**（25%） |
| 图集解码后的像素 | 2580 万（103 MB） | 1310 万（52 MB） |

- 音效：VBR MP3，LAME V0 质量（单声道平均约 127 kbps，比原版音效的码率还高），44.1 kHz 单声道不变。解码后的长度和原 WAV 一样（LAME 头里的编码延迟会被裁掉）。clip 名字不变，所以 .sound_info 不用改。没有任何 .sound_info 播放的音效不打包（目前 1 个：`league_yone_sfx_e_mark`）。
- 图集：每个 `#anim.fanim` 里引用的帧，像素完全相同的只留一份，按高度分行紧凑排列，帧之间留 1 px 透明缝，宽高都不超过 2048。每一帧的宽高、像素、时长都不变，只改 .fanim 里的 x、y。原来的图集按 2048 宽排成一长条，一半以上是空白。
- JSON：只删字符串外面的空白，数字和字符串的原文一字不改。
- 每个输出都和源文件核对：JSON 解析后相同，每一帧逐像素相同，MP3 解码长度相同。lint 0/0，INFO 和源文件逐条相同。模拟器里 50 局（41 个英雄各一局 + 9 局全联盟阵容，每局 10 分钟）打包前后结算数据逐项相同。

2026-10-02 装进游戏：把当时的安装（main 的 41 个英雄 + 还没合并的青钢影 + 在测的李青）原样打包，一次性写进新文件夹，再和 `mods/league` 对调（旧的留作 `Teamfight Manager2/league_backup_pf`），然后装上剑姬修复。同一块机械盘、同样绕过缓存读取（每次先读 250 MB 别的数据冲掉硬盘自带的缓存），各测两次：

| | 文件 | 大小 | 冷读取 |
|---|---|---|---|
| 原来的 `mods/league` | 1560 | 78.1 MB | 16.2 / 16.0 秒（每个文件 10.4 ms） |
| 打包后的 `mods/league` | 1559 | 19.4 MB | 4.0 / 4.1 秒（每个文件 2.6 ms） |

文件数几乎没变，每个文件的读取时间却降到四分之一：字节少了，而且一次性按游戏读取的顺序写进去的文件在盘上是连续的，寻道少了。原来的安装是各个会话一个英雄一个英雄陆续写进去的，散在盘上各处。

## 2. 比赛里的 CPU

### 怎么测的

- 用 mod SDK 里的 game_core（和游戏同一套模拟代码）跑 5v5，`QueryThreadCycleTime` 记录每 tick 用掉的 CPU 周期（`tools/perf/tick.rs`）。只计本线程的周期，别的会话同时在跑模拟也影响不大。
- 用采样分析找热点（`tools/perf/profile.py`）：每 2 ms 暂停一次线程，用 dbghelp `StackWalk64` 回溯调用栈，用链接器 map 文件把地址对应到函数名。
- 用法见第 6 节。

### 发现 1：每 tick 复制 skill、skill2

- 屏幕上正在放的比赛，每 tick 都要调用 `AbstractGame::build_entity_state_event` 生成实体状态。它对每个英雄调用 `ChampionInfo::skill()` 和 `skill2()`，mod 英雄（`ModChampionEntry`）的实现会把整个技能定义（含完整效果树）复制一份，读完冷却等数值再丢掉。
- 金克丝镜像局里，55% 的 CPU 花在复制和释放金克丝的 skill2 上。
- 后台模拟（不生成事件，例如赛季里别的队伍的比赛）没有这一步：同一局金克丝镜像局 24 万周期/tick，原版阵容 22 万（+8%）。
- 所以开销和 skill、skill2 的节点数成正比，和大招无关。

一个联盟英雄替换一个原版英雄上场，整局每 tick 的 CPU 多出多少（main c5a99af + 剑姬修复，5 分钟对局，2 套阵容 × 3 个种子，屏幕上的比赛）：

| 英雄 | 整局每 tick CPU | skill 节点 | skill2 节点 |
|---|---|---|---|
| 金克丝 | +89% | 10 | 1019 |
| 布里茨 | +71% | 481 | 278 |
| 菲奥娜 | +70% | 375 | 378 |
| 崔丝塔娜 | +69% | 337 | 342 |
| 永恩 | +63% | 276 | 465 |
| 艾克 | +63% | 66 | 630 |
| 凯尔 | +63% | 335 | 355 |
| 黛安娜 | +49% | 33 | 491 |
| 凯特琳 | +48% | 32 | 457 |
| 伊泽瑞尔 | +44% | 269 | 121 |
| 阿狸 | +43% | 378 | 38 |
| 塔里克 | +39% | 94 | 234 |
| 魔腾 | +37% | 55 | 260 |

其余 28 个英雄在 +2%（提莫）到 +32%（维迦）之间。10 个联盟英雄同场时，每 tick 的 CPU 约是 10 个原版英雄的 4 倍（120–136 万周期 vs 32 万）。

### 发现 2：剑姬 W 的残留投射物

- 剑姬 W 的特效 `league_fiora_w_guard_fx` 原来是 `TargetProjectile`，速度 100，没有任何效果，只用来显示格挡的画面。它追着目标飞，速度太慢追不上，一直留在场上：一局里有的活了 11214 tick（3 分钟），有的到对局结束还在。画面的最后一帧是 1×1 的空白、时长 8 秒，所以看不见。
- 投射物每次运行都要调用 `prepare_dead_caster_overlay`：施法者已经死了，就从阵亡列表里把施法者整个复制一份（`Entity::clone`，包括 4 个技能的完整效果树）。剑姬（约 2000 个节点）一死，每个残留的投射物每 tick 都要复制一次她。
- 实测：剑姬死亡那一刻，整局每 tick 的开销从 110 万周期跳到 290–360 万，一直持续到对局结束。双剑姬对局里 34.5% 的 CPU 花在这里。
- 修复：改成 `LinearProjectile`，速度、高度偏移、画面都不变，射程 4500，也就是 45 tick（画面可见的 0.75 秒）后自动消失；`applied_target` 用 `Ally`，因为放在 `Enemy` 上时敌方 AI 会对这个纯画面的投射物做出反应（同种子对局不同），和厄运小姐 R 的波浪画面是同一个问题（champion-data.md "Gotchas"）。

| 15 分钟对局，8 个种子，屏幕上的比赛 | 修复前 | 修复后 |
|---|---|---|
| 一方有剑姬，每 tick 平均 | 135 万周期 | 81 万周期（−40%） |
| 双方各一个剑姬 | 268 万周期 | 109 万周期（−59%） |

残留的投射物本身会影响敌方 AI，所以修复后同种子的对局过程不再完全一样。强度没有变化（菲奥娜上路对 6 个原版上单 × 3 套阵容 × 两边 × 8 个种子，各 288 局）：

| | 击杀差 | 输出 | 承伤 | 治疗 | KDA |
|---|---|---|---|---|---|
| 修复前 | +1.94 | 11833 | 10198 | 5923 | 3.7 / 1.6 / 2.9 |
| 修复后 | +1.89 | 11828 | 10333 | 5835 | 3.6 / 1.7 / 3.0 |

### 换算成游戏里的时间

- 原版英雄 10 人对局约 26 万周期/tick（这台 CPU 上约 60 µs）。10 个联盟英雄约 120–140 万周期/tick（约 0.3 ms）。游戏 1 倍速每秒 60 tick，3 倍速 180 tick。
- 单看平均值，全联盟对局 3 倍速时每秒约多用 50 ms CPU，主要在内存分配上（每次复制都是成千上万次小块分配）。剑姬那种残留会随对局时间累积，最高单 tick 达到 2000 万周期（约 5 ms）。
- lint 现在会对这两类问题给出提示：skill/skill2 超过 300 个节点时给 INFO，追踪投射物速度低于 1000、或直线投射物存活超过 600 tick 时给 WARN。

## 3. 图鉴、选人界面

- 选人卡片和图鉴会画每个英雄的待机帧，图集要解码成 RGBA 再上传显卡。
- 原版 83 张英雄图集解码后 133 MB；我们 41 个英雄的图集（含特效）原来 103 MB，打包后 52 MB。
- 没有确认图集是启动时解码还是第一次画的时候才解码（*inferred*：exe 里同时带了 Rust 的 png 库和 Skia 的 libpng）。两种情况下打包后的解码量和显存都减半。
- 2026-10-24：PPU 英雄多了以后这就是选人界面、英雄界面卡的原因（游戏 256 MiB 的图片缓存装不下），界面改画小图集，见第 9 节。

## 4. 安装和上传

见 README 的"安装测试"。要点：

- 装进游戏一律用 `tools/package_mod.py`，不要再直接复制 `league/` 或 WAV。
- 只装一个英雄：`python tools/package_mod.py --hero <英雄> --install`。只写这个英雄的文件，共享的 i18n、champion_view、override_info 只刷新这个英雄的键，mod_info 取较高版本；同名的 .wav 会被换成 .mp3，2026-10-17 以前装在 `sound/sfx/` 的那份音频会删掉（现在装在 `sound/bgm/`，第 7 节）。别的英雄的文件不动，所以几个英雄会话可以同时装。
- 全部装：`python tools/package_mod.py --install`。只在没有别的英雄正在测试时用。
- 上传创意工坊：`python tools/package_mod.py --out <上传用文件夹>`，再用 TFM2ModUploader 上传那个文件夹。
- 仓库里的源文件（漂亮格式的 JSON、WAV、宽松的图集）保持原样，各英雄分支照常改，不会因为打包产生冲突。

## 5. 还能做的（需要逐个确认）

1. **技能树瘦身**：2026-10-18 做了一轮（第 8 节）：打包时的通用化简加 17 个英雄的等价改写，全部 skill + skill2 −7.7%。剩下的大树（金克丝 E 1017、劫 W 785、艾克 W 630、黛安娜、布里茨、凯特琳……）在数据里没有更省的等价写法：艾克 W 那 91 段原地画面、金克丝 20 段夹子都是在某个位置上逐 tick 排好的延迟效果，改成一段动画会改变画面（球被碰到就要立刻碎），要省只能动设计。
2. **向开发组反馈**：两处都是引擎内部的复制，修在引擎里所有 mod 都受益：`ModChampionEntry::skill()/skill2()` 每次调用都克隆整个 `DataActionDef`；`prepare_dead_caster_overlay` 对每个施法者已死的投射物每 tick 克隆整个 `Entity`。
3. 定期整体重装：一个英雄一个英雄地装（`--hero`）会让文件又散开。机械盘上隔一段时间用 `--out` 打一份完整的包，像第 1 节那样整个换掉 `mods/league`，冷读取能保持在 4 秒左右。

## 6. 复现方法

1. **每 tick 的 CPU**：`tools/perf/tick.rs` 和平衡模拟器 `sim3.rs` 一样用 mod SDK 编译（把 build.sh 里的文件名换掉），在放着 `sim/assets/` 的文件夹里运行：

   ```bash
   tick.exe 300 1 <蓝方上 野 中 下 辅> <红方上 野 中 下 辅>     # 每个是 .data_champion 路径或 base:<id>
   ```

   第一行的 `cyc_tick_mean` 是每 tick 的平均周期数。`TICK_MODE=view`（默认）是屏幕上的比赛，`plain` 是后台模拟，`sparse` 每 60 tick 才生成一次事件（对局和 view 完全一样，快一倍，还能拿到结算）；`TICK_STATS=1` 打印结算，`TICK_PROJ=1` 列出活了 600 tick 以上的投射物。
2. **热点函数**：编译 tick.rs 时加 `-C link-arg=/MAP:tick.map`，然后 `python tools/perf/profile.py tick.exe tick.map 300 1 <10 个英雄>`，会列出各函数占的样本比例，以及效果树复制是从哪里调用的。
3. **冷读取**：用 `FILE_FLAG_NO_BUFFERING` 打开文件读取，绕过系统缓存；先读几百 MB 别的数据，冲掉硬盘自带的缓存。
4. **引擎行为**：游戏 exe 里的字符串和 Rust 源文件名（`engine-core\src\assets.rs`、`engine-backend-skia\src\platform.rs` 等）可以定位到函数；SDK 的 `libengine_core` rmeta 里能看到 `SoundData { FilePath, BundleRange }`、`RegisterSoundFile` 等类型名。

## 7. 少开文件：音频放 `sound/bgm/`（2026-10-17）

用户：「游戏现在加载会卡很长时间 查一下原因帮我 能优化就优化」。那次启动 72 秒：装好的 league 已经 119 个英雄、5282 个文件，又被一个个英雄的安装写得散在盘上。把整个文件夹按顺序重写一遍后，第二次启动只要 7 秒；但这只对这台电脑有效，创意工坊玩家的文件是 Steam 写的。启动的开销按**文件个数**算（机械盘上每个文件一次寻道，更新后每个新文件被 Windows Defender 扫一次），能帮到玩家的只有让游戏启动时少开文件。

### 引擎（0.6.4 exe 反汇编 + 官方文档 + 实测）

- 加载器（engine-core `assets.rs`）把 mod 的每个文件读进内存，只有扩展名是 .mp3 / .wav、路径里含 `/sound/bgm/` 的登记成 `SoundData::FilePath`，播放时才打开。mod 不能带 `bundle.game_data` 那样的打包文件（只有原版用）。
- `Sfx` / `TargetSfx`（game-view `set_feedback.rs`）拼出 `asset/base/sound/sfx/<名字>`，经 `mod.override_info` 换成 mod 里的路径，再取那个路径上的 `SoundInfo`：一个路径只放一个资源，没有就记 `sound_info not found:`，**不会退回去直接播音频**。所以每个音效事件都要自己的 .sound_info，一个文件装不下几个事件；`plays` 里的 clip 也按名字 `asset/base/sound/sfx/<clip>` 经 override 找。
- 单次播放（engine-backend-skia `platform.rs`）在调用它的线程（主线程）里同步查资源、打开文件（调用链走到 `CreateFileW`），解码和混音在音频线程。
- 原生 DLL 在 `asset loading done!` 之后才初始化，所以 `league.dll` 管不了启动时的读文件。
- 官方文档（teamsamoyed/TeamfightManager2Mod `docs/`）没写音效；图标可以合成一张图（英雄数据用 `skill_icon: {source, tags}`），动画可以直接放 `.aseprite`。

### 测法

D 盘（5900 转机械盘）上一份测试用的游戏：exe、`bundle.game_data`、Steam DLL 都是硬链接，自己的 config（窗口 800×450、静音，只启用 league）。每个变体从已安装的 0.132.0（119 个英雄）生成，时间取 log.log 的 `first render done!` → `asset loading done!`。

- **热**：文件在系统缓存里、已经扫描过（平常第二次启动）。
- **刚写入**：刚写进去还在缓存里，第一次打开时 Defender 要扫描（玩家下载或更新后马上开游戏）。
- **冷（连续 / 分散）**：无缓冲打开每个文件把它清出系统缓存，再无缓冲读 400 MB 别的文件冲掉硬盘自带的缓存。连续 = 按顺序一次写完（像整体重装），分散 = 按随机顺序写（像 Steam 下载；这块盘上每个文件约 16 ms）。
- **刚写入 + 冷（分散）**：无缓冲写入（不进缓存、没扫描过）后启动：更新后隔一段时间或重启后第一次开。

不装 mod 时热启动 0.35 秒，原版资源包冷读 11.3 秒。

### 结果（秒）

| 变体 | 启动读的文件 | 热 | 刚写入 | 冷（连续） | 冷（分散） | 刚写入 + 冷（分散） |
|---|---|---|---|---|---|---|
| 原来的打包 | 5282 | 0.63 | 16.1 | 3.67 | 87.9 | 101.2 |
| 音频放 `sound/bgm/` | 3194 | 0.75 | 8.45 | 2.94 | 51.4 | 61.7 |
| 再加特效按英雄合并、技能图标合成一张图（没做） | 2603 | 0.69 | 6.64 | 2.43 | 41.5 | 51.5 |

其他会话的模拟占满 CPU、内存时，同一测试会慢不少（刚写入 + 冷：101 → 144 秒），比较都在相邻的时间里做。

### 比赛里第一次播放，和 league.dll 的预读

测试游戏里放了一个只读的原生探针（按帧用 `play_sound` 播指定的音效，记每帧耗时，不进仓库）：

- 放在 `sound/bgm/` 的音频经 override 找到、正常播放，没有报错（对照：不存在的路径记 `sound not found:`）。
- 文件**不在系统缓存里**时，第一次播放要在主线程等一次读盘：机械盘上文件分散时一个 15–30 ms，同时第一次响 6 个有一帧超过 100 ms（引擎把单帧截在 100 ms）。
- 文件**在缓存里**时没有额外开销：播放前 5 帧确认在缓存里（读一次 0.1 ms），首次播放的停顿中位 5.5 ms，原版的内存音效 6.7 ms。同一次游戏里重播也不卡。
- 所以 `league.dll` 0.7.27（`addons/league_main/src/warm.rs`）在标题画面出来后，用一个线程把 `sound/bgm/` 的文件按在盘上的先后（每个文件第一个簇）读一遍：2088 个、37 MB，冷盘 2.4–5 秒。线程 CPU 优先级最低、每个文件按低 I/O 优先级读。**不能用线程的后台模式**：它把读进来的页也标成最低内存优先级，测试时这台电脑内存很紧（可用约 2 GB），预读完十几秒后再读，12 个里 11 个又要等盘；改成普通内存优先级后 12 个都还在缓存里，三批「6 个新音效同时第一次响」超出 15.5 / 8.0 / 7.8 ms，和原版音效（13.5 ms）一样。
- Mac / Linux 没有 DLL，就没有预读：固态盘上第一次播放读一个文件不到 1 ms，机械盘上会偶尔卡一下。

### 没做的

- 特效按英雄合并（旧路径用 override 指向合并后的图，数据和附加包都不用改）：少 236 个文件；30 个英雄的几张图有同名标签，只能合一部分。
- 技能图标合成一张图：少 355 个，但 league_addons 的约 60 个英雄有自己的 data 副本，按单个图标文件引用，要和附加包一起改。
- 这两项是一起测的（上表第 3 行）；按文件数折算，特效约省 4 秒、图标约 6 秒（分散冷启动）。
- 合并音效事件：引擎一个路径一个 SoundInfo，做不到；完全相同的 .sound_info 只有 4 个。
- `.aseprite` 单文件（一个文件出 `#sheet` 和 `#anim`）能少 391 个，但引擎自己重新排帧，可能挪动像素，`league.dll` 也按图集路径认身体。

## 8. 技能树瘦身（2026-10-18）

用户：「开一个单独的会话做技能树瘦身，先做剑姬、金克丝、劫，每位等价改写、模拟核对」，之后「能优化的英雄都优化吧」。游戏每 tick 都要把每个 mod 英雄的 skill、skill2 整棵复制一遍（第 2 节「发现 1」）；过日时当天比赛打完后那 1–2 分钟的单线程段，采样到的热点也是递归复制加堆分配（`TeamfightManager2.exe+0x1092e40`，附加包代码不在栈上）。树越大越慢。要求：游戏里的效果（伤害、控制、时机、画面）一点不变。

### 什么算"等价"

- 同样的效果、同样的顺序、同样的目标和时机，对英雄能进入的每一种 buff 状态都成立。
- **AI 和敌人随时都在读技能树**，读的是施法者当前 buff 选中的那一支（伤害、治疗、护盾的估值），不只是施放前读：技能冷却中、刚放完的那一两 tick 也读。施放中临时用的标志要在同一次执行里摘掉，不能留到下一 tick。
- `RandomTarget` 会抽游戏的随机数：同一个英雄的 `RandomTarget` 必须在同样的施放里、按同样的顺序执行。投射物不能增减、不能换顺序。
- 靠"某个标志在某种情况下一定不在"化简时，要从整个英雄（attack、skill、skill2、ult、附加包副本和它的 Rust 代码）里每一处加、删这个标志推出来，写进脚本的说明。**技能冷却不能当下限**：原版吟游诗人的大招（原生代码）引导 240 tick、每 3 tick 把范围内友军的技能冷却砍一半，金克丝的 E 放完 261 tick 就能再放（冷却 600）。
- 引擎对隐藏标志的增删本身也敏感：金克丝每次放 E 多挂一个谁都不读的 1 tick 标志，72 局里有 1 局在几百 tick 后某个单位的走位差了一点，之后整局不同。能保持原来的标志操作就保持；改了的，下面的核对都通过了。

### 怎么核对

[`tools/perf/trace.rs`](../tools/perf/trace.rs)（和 sim3 一样用经典 SDK 编译）把一局里每 tick 的全部事件——移动、动作、动画、伤害、治疗、控制、投射物、特效、音效、每个单位的 buff 名单和冷却——算成一个指纹；[`tools/perf/same_games.py`](../tools/perf/same_games.py) 用同样的种子把改前、改后（按打包后的样子）各跑一遍，逐 tick 比指纹。同一份数据跑两遍，指纹逐 tick 相同（引擎从哈希集合里打印的两处已排序）。改名或改时长的隐藏标志（没有 `view_buffs` 画面、不带属性）用 `TRACE_HIDE` 从 buff 名单里去掉再比。逐 tick 相同，伤害、击杀、胜负、画面、音效也就逐局相同。

### 两层做法

1. **打包时的通用化简**（[`tools/kit/slim.py`](../tools/kit/slim.py)；`tools/package_mod.py` 和 `addons/league_addons/assemble.py` 都会调用，仓库里的源文件不变，以后的新英雄自动受益）：拼平嵌套的 Combine（WithSelf、RangeEffect 这类对多个单位执行的列表里只拼只含一个效果的）、去掉只包一个效果的 Combine、两个分支相同的 SwitchByBuff 合一、两个分支开头或结尾相同的效果提到分支外面（开头的只在它们不碰这个 buff 时提）。单独这一层：全部 123 个英雄和 63 份附加包副本的 skill + skill2 少约 5%。
2. **按英雄的等价改写**（各自的生成脚本：`tools/kit/build_<英雄>.py`，或 `tools/fix/` 下新的脚本，每个脚本的说明里写着为什么等价）。

## 9. 选人界面、英雄界面卡：界面改画小图集（2026-10-24）

用户：「PPU导致页面卡 特别是英雄界面 还有BP界面非常的卡」「我怀疑这个导致BP界面卡顿 但是局内不卡」，以及用户自己的判断「BP页面会解码完整战斗图集来获取立绘和头像，用PPU的多了会撑爆256mb的缓存，导致每一帧都在重新解码」。没有实机采样（用户：「先不实测，根据代码和贴图大小直接给出结论和修复方案」），结论来自代码、贴图大小和 0.6.5 exe 的静态反汇编。

### 原因

- 游戏的图片缓存预算是 256 MiB。Rin 的 PPU Core 使用说明里有同样的经过：0.2.16 把它提到 512 MiB，治「多张大型精灵图共用原生 256 MiB 缓存时的重复解码」；0.2.18 撤掉扩容，改成 BP 中央列表的小人和头像用独立小图，实机「显示正常，悬停流畅」。
- 界面画英雄的五处——BP 格子（`0x20da020`）、图鉴 / 头像（`0x29e6740`）、选人位（`0x29e2900`，通用的「按名字和动作画一帧」）、选中特写（`0x22feb50`）、记分板头像（实体绘制里）——都按名字取英雄整张的战斗图集：自己先取一次算 UV，再把名字交给 `0x1be5d0`（建绘制命令，BP 格子、记分板、选中特写的调用方）或 `0x2172320`（图片节点，图鉴、选人位），真正画的时候游戏按这个名字再取一次。画一个 40 像素的小人，整张图集也得在缓存里。
- 当时装着的 167 张英雄图集解码后 589 MiB：93 个 PPU 英雄 493 MiB，74 个 1x 英雄 96 MiB（全是 1x 的话约 215 MiB，装得下）。BP 和英雄界面一屏画出全部英雄，超出预算一倍多；局内只有十个英雄，装得下，所以不卡。
- 不是 league.dll 钩子的开销：表的拷贝都有缓存（league.log 里没有反复重建），每张卡几微秒。

### 做法

- `tools/package_mod.py` 给每个英雄打出两张小图集，像素原样、相同的帧合并：`ui_sheets/idle/<英雄>`（`idle`：PPU 英雄的 lo_idle）给图鉴、头像、选人位、选中特写、记分板；`ui_sheets/bp/<英雄>`（`bp`、`dead`：hd_bp / hd_dead）只给 BP 格子。idle 四周留整张图集里一样的空白边（头像按脸点裁，会裁到帧外），reel 和 dead 上方留足、其余三边一个游戏像素（卡片往帧上方多画，泰达米尔、库奇、斯莫德的卡片露出过上面那帧）。全部英雄解码后 idle 28 MiB、bp 137 MiB。
- league.dll 0.7.140（[`src/ui.rs`](../addons/league_main/src/ui.rs)）：这五处取动画表时给游戏那张表的一份拷贝，每个动作的帧换成小图集里的（BP 格子每个动作是 reel、dead 是 dead；别处每个动作是 idle），矩形的除数和以前一样，画出来大小、锚点不变；紧接着它们自己取图时给小图集的条目；两个接名字的函数入口各挂一段保存寄存器的跳板，交出去的名字正是刚换过图的那个，就换成小图集的名字。别的调用原样放过，战场不动。地址在 build.rs 里列出（0.6.5），别的版本由 game_places 从这五处的调用里找；找不到、或英雄没有小图集（别的模组、还没打包），照旧画整张图集。
- BP 界面要留在缓存里的英雄图从 589 MiB 降到约 140 MiB（idle 的只有画出来的那几个），英雄界面约 28 MiB。

### 没做的

- 战斗图集里的 lo_ 帧（140 MiB）界面已经不读，可以从图集里删掉，省内存和加载时间；等实机确认小图集没问题再做。
- BP 格子还有一种「播一次某个动作再回 idle」的状态（`banpick_champion_slot.rs` 动画状态 4），没查到什么时候出现；出现时现在画的是 reel。

## 10. 游戏的 GPU 图片缓存：256 MiB → 1 GiB（2026-10-30）

用户：「能强制改缓存吗 游戏的」「先收尾，再扩缓存」。第 9 节的小图集让 BP 和英雄界面装得下，但 `tools/ci/ui_sheets.py` 给 BP 小图集留的 192 MiB 到石傲玉（tft 第 20 位）已经满了（191.7 MiB，他的选人卡片只能放两段动作）。

### 缓存是什么

- 游戏用 Skia 画图（EXE 里的 `skia-bindings`，GPU 后端 Ganesh）。贴图上传后放在 Skia 的 `GrResourceCache` 里，预算是 Skia 默认的 `kDefaultMaxBudget` = 256 MiB：0.7.0 的构造函数在 rva `0x3716120`，`mov qword [rdi+0x70], 0x10000000` 就是 `fMaxBytes`；后面两个消息信箱、上下文 ID（+0xe8 / +0xec）、`fSingleOwner`（+0xf0）和 Skia 源码的成员一一对应。
- `insertResource`（`0x3716b40`）：`fBytes`（+0x78）加上大小，计入预算的再 `fBudgetedCount`（+0x80）加一、`fBudgetedBytes`（+0x88）加上大小，最后跳到 `purgeAsNeeded`（`0x3716960`）；`purgeAsNeeded` 每次刷新比较 `fBudgetedBytes > fMaxBytes`，超了就从最久没用的开始清。一屏要的贴图超过 256 MiB 时，每帧都在清掉、重新上传——就是第 9 节的「每一帧都在重新解码」。
- 游戏自己从来不调 `setLimit`（`fMaxBytes` 只在构造函数里写）。Rin 的 PPU Core 0.2.16 把它提到过 512 MiB，0.2.18 撤掉改成小图集（撤的原因没有记录）。

### 做法

- league.dll 0.8.16 [`src/cache.rs`](../addons/league_main/src/cache.rs)：GPU 上下文在 mod 加载前就建好了，改构造函数来不及，所以改正在用的那个缓存对象。`insertResource` 开头 13 字节（几个 push、`sub rsp`、两个寄存器 mov，没有 rip 相对的操作数）换成跳到一小段机器码：`fMaxBytes` 还是 256 MiB 就改成 1 GiB，并记下缓存对象的地址，然后执行原来的开头、跳回去。不调用 Rust，只改标志位。游戏或别的 mod 设过别的上限就不动。
- 找函数：`insertResource` 开头 64 字节的特征码（两个 call 的位移挖空）和构造函数里 `fMaxBytes = 256 MiB; fBytes = 0` 两句，在 `.text` 里必须各找到一处，才挂（`cargo test -p league_main` 拿本机的 EXE 核对）。任一个不对就不挂，日志写原因，游戏照旧 256 MiB。和 build.rs 列的版本无关：认不得的游戏版本也会试。
- 日志：league.log 里 `GPU cache`：挂上了没有、缓存对象的地址、用量每过 64 MiB 的新高。
- 1 GiB 而不是更多：这台机器 31 GB 内存，游戏跑在 AMD 核显上（显存就是系统内存），1 GiB 只是上限，用到多少才占多少。
- `tools/ci/ui_sheets.py` 的预算跟着放大到缓存的四分之三 / 四分之一：BP 768 MiB、idle 256 MiB；石傲玉的选人卡片恢复四段。缓存补丁没挂上的游戏版本（league.log 写 `GPU cache left at 256 MiB`）上，BP 界面又会在英雄多时卡，到时按日志重找函数。
