# 性能：英雄多了以后加载慢、比赛卡顿（2026-10-02）

用户反馈："这游戏 mod 英雄多了后加载卡顿变慢"。这份文档记录查到的原因、实测数字、已经做的改动和还能做的事。数字都是实测的；只靠推断的地方会标出来。

## 结论

| 现象 | 原因 | 改法 | 效果 |
|---|---|---|---|
| 启动慢 | 游戏启动时把 mod 里除背景音乐外的每个文件整个读进内存。装好的 league 是 78 MB、1560 个文件，其中 WAV 音效 66 MB。这台电脑的游戏装在机械硬盘上，冷启动光读这些文件就要 16 秒 | 安装和上传都用 `tools/package_mod.py` 打包：音效转 MP3、图集去重重排、JSON 去空白 | 78 MB → 19 MB；机械盘冷读取 16.1 秒 → 4.1 秒 |
| 有剑姬的比赛越打越卡 | 剑姬 W 的特效投射物速度只有 100，又追着目标飞，能在场上留好几分钟。剑姬一死，引擎每 tick 都要为每个残留的投射物把死掉的剑姬整个复制一遍（包括 4 个技能的完整效果树） | 改成飞 4500 距离就结束的直线投射物，画面不变（用户已批准） | 15 分钟对局每 tick 的 CPU：一个剑姬 −40%，双方各一个 −59% |
| 比赛里 mod 英雄越多越吃 CPU | 屏幕上正在放的比赛里，引擎每 tick 为每个 mod 英雄把 skill、skill2 两棵效果树各复制一遍再丢掉 | 建议把最大的几个技能瘦身（还没改，要逐个英雄确认） | 10 个联盟英雄的对局每 tick CPU 约是原版英雄的 4 倍 |
| 选人、图鉴界面 | 每个英雄的图集都要解码成 RGBA。原来的图集一半是空白 | 打包时去掉重复帧、紧凑重排 | 解码后 103 MB → 52 MB |

## 1. 启动加载

### 引擎怎么读 mod

从 `TeamfightManager2.exe`（0.6.2）的字符串和反汇编看到的：

- mod 文件夹由 engine-core `assets.rs` 的加载器逐个文件读取。只有 `/sound/bgm/` 下的 .wav/.mp3 登记为流式播放，**其余每个文件都在启动时整个读进内存**，包括全部音效。所以音效体积直接等于启动时的读盘量和常驻内存。
- 音频只支持 .mp3 和 .wav。别的格式（.ogg）会提示 `Unsupported audio file "{Path}". Only .mp3 and .wav are supported.`
- 音效第一次播放时，把内存里的字节复制进缓存；每次播放都在音频线程里用 rodio 0.21 + symphonia 0.5.4 边播边解码，不在启动时解码，也不占主线程。
- 原版 498 个音效全是 MP3（大多 192 kbps 立体声，带 LAME 头），所以换成 MP3 走的是引擎本来的路线。
- 日志：即使 `config/game/base.json` 里 `"log": false`，`%APPDATA%\TeamSamoyed\TeamfightManager2\data\log.log` 也会写 `state init done..` 和 `asset loading done!` 两行，时间差就是资源加载用时。

### 这台电脑上的实测

游戏在 D 盘：一块 5900 转的机械硬盘（ST2000DL001），不是固态。

| 测量 | 结果 |
|---|---|
| 绕过 Windows 文件缓存，按目录顺序读完 `mods/league`（相当于冷启动） | 1560 个文件、78.1 MB，**16.1 秒**（4.8 MB/s，平均每个文件 10 ms，主要花在寻道） |
| 其中 WAV | 646 个、65.9 MB，8.7 秒 |
| 其余小文件 | 914 个、12.2 MB，7.4 秒 |
| 7 月 13 日日志里的资源加载（当时启用的是 lol_mod） | 18.2 秒 |
| 今天 10:11（文件还在系统缓存里） | 3.9 秒 |

对比：C 盘的 NVMe 固态上，仓库里的 `league`（76.5 MB、1516 个文件）同样绕过缓存读一遍只要 0.7–0.9 秒。所以"加载慢"主要出在机械硬盘的冷启动上。

另外，文件第一次被打开时 Windows Defender 会扫描它（实时保护开着）：刚写进去的文件第一次读，固态上每个文件 6–11 ms，机械盘上新文件夹第一次读要 22.9 秒；扫描结果有缓存，之后就快了。病毒库更新后会重新扫描，文件越小、越少，这一步越快。

### 打包后

`python tools/package_mod.py`（41 个英雄，main c5a99af + 剑姬修复）：

| 文件 | 打包前 | 打包后 |
|---|---|---|
| 音效 .wav → .mp3 | 64.5 MB | 11.7 MB |
| .data_champion | 6.4 MB | 1.7 MB |
| .png（图集、图标） | 4.6 MB | 4.5 MB |
| 其他 JSON | 1.1 MB | 1.0 MB |
| 合计 | **76.5 MB** | **19.0 MB**（25%） |
| 图集解码后的像素 | 2580 万（103 MB） | 1310 万（52 MB） |

- 音效：VBR MP3，LAME V0 质量（单声道平均约 127 kbps，比原版音效的码率还高），44.1 kHz 单声道不变。解码后的长度和原 WAV 一样（LAME 头里的编码延迟会被裁掉）。clip 名字不变，所以 .sound_info 不用改。没有任何 .sound_info 播放的音效不打包（目前 1 个：`league_yone_sfx_e_mark`）。
- 图集：每个 `#anim.fanim` 里引用的帧，像素完全相同的只留一份，按高度分行紧凑排列，帧之间留 1 px 透明缝，宽高都不超过 2048。每一帧的宽高、像素、时长都不变，只改 .fanim 里的 x、y。原来的图集按 2048 宽排成一长条，一半以上是空白。
- JSON：只删字符串外面的空白，数字和字符串的原文一字不改。
- 每个输出都和源文件核对：JSON 解析后相同，每一帧逐像素相同，MP3 解码长度相同。lint 0/0，INFO 和源文件逐条相同。模拟器里 50 局（41 个英雄各一局 + 9 局全联盟阵容，每局 10 分钟）打包前后结算数据逐项相同。

2026-10-02 装进游戏：把当时的安装（main 的 41 个英雄 + 还没合并的青钢影 + 在测的李青）原样打包，一次性写进新文件夹，再和 `mods/league` 对调（旧的留作 `Teamfight Manager2/league_backup_pf`），然后装上剑姬修复。同一块机械盘、同样绕过缓存读取（每次先读 250 MB 别的数据冲掉硬盘自带的缓存），各测两次：

| | 文件 | 大小 | 冷读取 |
|---|---|---|---|
| 原来的 `mods/league` | 1560 | 78.1 MB | 16.2 / 16.0 秒（每个文件 10.4 ms） |
| 打包后的 `mods/league` | 1559 | 19.4 MB | 4.0 / 4.1 秒（每个文件 2.6 ms） |

文件数几乎没变，每个文件的读取时间却降到四分之一：字节少了，而且一次性按游戏读取的顺序写进去的文件在盘上是连续的，寻道少了。原来的安装是各个会话一个英雄一个英雄陆续写进去的，散在盘上各处。

## 2. 比赛里的 CPU

### 怎么测的

- 用 mod SDK 里的 game_core（和游戏同一套模拟代码）跑 5v5，`QueryThreadCycleTime` 记录每 tick 用掉的 CPU 周期（`tools/perf/tick.rs`）。只计本线程的周期，别的会话同时在跑模拟也影响不大。
- 用采样分析找热点（`tools/perf/profile.py`）：每 2 ms 暂停一次线程，用 dbghelp `StackWalk64` 回溯调用栈，用链接器 map 文件把地址对应到函数名。
- 用法见第 6 节。

### 发现 1：每 tick 复制 skill、skill2

- 屏幕上正在放的比赛，每 tick 都要调用 `AbstractGame::build_entity_state_event` 生成实体状态。它对每个英雄调用 `ChampionInfo::skill()` 和 `skill2()`，mod 英雄（`ModChampionEntry`）的实现会把整个技能定义（含完整效果树）复制一份，读完冷却等数值再丢掉。
- 金克丝镜像局里，55% 的 CPU 花在复制和释放金克丝的 skill2 上。
- 后台模拟（不生成事件，例如赛季里别的队伍的比赛）没有这一步：同一局金克丝镜像局 24 万周期/tick，原版阵容 22 万（+8%）。
- 所以开销和 skill、skill2 的节点数成正比，和大招无关。

一个联盟英雄替换一个原版英雄上场，整局每 tick 的 CPU 多出多少（main c5a99af + 剑姬修复，5 分钟对局，2 套阵容 × 3 个种子，屏幕上的比赛）：

| 英雄 | 整局每 tick CPU | skill 节点 | skill2 节点 |
|---|---|---|---|
| 金克丝 | +89% | 10 | 1019 |
| 布里茨 | +71% | 481 | 278 |
| 菲奥娜 | +70% | 375 | 378 |
| 崔丝塔娜 | +69% | 337 | 342 |
| 永恩 | +63% | 276 | 465 |
| 艾克 | +63% | 66 | 630 |
| 凯尔 | +63% | 335 | 355 |
| 黛安娜 | +49% | 33 | 491 |
| 凯特琳 | +48% | 32 | 457 |
| 伊泽瑞尔 | +44% | 269 | 121 |
| 阿狸 | +43% | 378 | 38 |
| 塔里克 | +39% | 94 | 234 |
| 魔腾 | +37% | 55 | 260 |

其余 28 个英雄在 +2%（提莫）到 +32%（维迦）之间。10 个联盟英雄同场时，每 tick 的 CPU 约是 10 个原版英雄的 4 倍（120–136 万周期 vs 32 万）。

### 发现 2：剑姬 W 的残留投射物

- 剑姬 W 的特效 `league_fiora_w_guard_fx` 原来是 `TargetProjectile`，速度 100，没有任何效果，只用来显示格挡的画面。它追着目标飞，速度太慢追不上，一直留在场上：一局里有的活了 11214 tick（3 分钟），有的到对局结束还在。画面的最后一帧是 1×1 的空白、时长 8 秒，所以看不见。
- 投射物每次运行都要调用 `prepare_dead_caster_overlay`：施法者已经死了，就从阵亡列表里把施法者整个复制一份（`Entity::clone`，包括 4 个技能的完整效果树）。剑姬（约 2000 个节点）一死，每个残留的投射物每 tick 都要复制一次她。
- 实测：剑姬死亡那一刻，整局每 tick 的开销从 110 万周期跳到 290–360 万，一直持续到对局结束。双剑姬对局里 34.5% 的 CPU 花在这里。
- 修复：改成 `LinearProjectile`，速度、高度偏移、画面都不变，射程 4500，也就是 45 tick（画面可见的 0.75 秒）后自动消失；`applied_target` 用 `Ally`，因为放在 `Enemy` 上时敌方 AI 会对这个纯画面的投射物做出反应（同种子对局不同），和厄运小姐 R 的波浪画面是同一个问题（champion-data.md "Gotchas"）。

| 15 分钟对局，8 个种子，屏幕上的比赛 | 修复前 | 修复后 |
|---|---|---|
| 一方有剑姬，每 tick 平均 | 135 万周期 | 81 万周期（−40%） |
| 双方各一个剑姬 | 268 万周期 | 109 万周期（−59%） |

残留的投射物本身会影响敌方 AI，所以修复后同种子的对局过程不再完全一样。强度没有变化（菲奥娜上路对 6 个原版上单 × 3 套阵容 × 两边 × 8 个种子，各 288 局）：

| | 击杀差 | 输出 | 承伤 | 治疗 | KDA |
|---|---|---|---|---|---|
| 修复前 | +1.94 | 11833 | 10198 | 5923 | 3.7 / 1.6 / 2.9 |
| 修复后 | +1.89 | 11828 | 10333 | 5835 | 3.6 / 1.7 / 3.0 |

### 换算成游戏里的时间

- 原版英雄 10 人对局约 26 万周期/tick（这台 CPU 上约 60 µs）。10 个联盟英雄约 120–140 万周期/tick（约 0.3 ms）。游戏 1 倍速每秒 60 tick，3 倍速 180 tick。
- 单看平均值，全联盟对局 3 倍速时每秒约多用 50 ms CPU，主要在内存分配上（每次复制都是成千上万次小块分配）。剑姬那种残留会随对局时间累积，最高单 tick 达到 2000 万周期（约 5 ms）。
- lint 现在会对这两类问题给出提示：skill/skill2 超过 300 个节点时给 INFO，追踪投射物速度低于 1000、或直线投射物存活超过 600 tick 时给 WARN。

## 3. 图鉴、选人界面

- 选人卡片和图鉴会画每个英雄的待机帧，图集要解码成 RGBA 再上传显卡。
- 原版 83 张英雄图集解码后 133 MB；我们 41 个英雄的图集（含特效）原来 103 MB，打包后 52 MB。
- 没有确认图集是启动时解码还是第一次画的时候才解码（*inferred*：exe 里同时带了 Rust 的 png 库和 Skia 的 libpng）。两种情况下打包后的解码量和显存都减半。

## 4. 安装和上传

见 README 的"安装测试"。要点：

- 装进游戏一律用 `tools/package_mod.py`，不要再直接复制 `league/` 或 WAV。
- 只装一个英雄：`python tools/package_mod.py --hero <英雄> --install`。只写这个英雄的文件，共享的 i18n、champion_view、override_info 只刷新这个英雄的键，mod_info 取较高版本；同名的 .wav 会被换成 .mp3。别的英雄的文件不动，所以几个英雄会话可以同时装。
- 全部装：`python tools/package_mod.py --install`。只在没有别的英雄正在测试时用。
- 上传创意工坊：`python tools/package_mod.py --out <上传用文件夹>`，再用 TFM2ModUploader 上传那个文件夹。
- 仓库里的源文件（漂亮格式的 JSON、WAV、宽松的图集）保持原样，各英雄分支照常改，不会因为打包产生冲突。

## 5. 还能做的（需要逐个确认）

1. **技能树瘦身**：skill/skill2 每 tick 被复制，节点最多的是金克丝 skill2（1019）、艾克 skill2（630）、戴安娜 skill2（491）、布里茨 skill（481）、永恩 skill2（465）、凯特琳 skill2（457）。常见的冗余：逐帧拼出来的特效链（艾克 W 用 91 组 Delayed + SwitchByBuff + ViewEffect 拼一段画面，可以改成一段动画）、同一段逻辑在 SwitchByBuff 的多个分支里各抄一份（金克丝 20 份 e_lock 检查）。简单的等价化简（拆掉单子项 Combine、合并嵌套 Combine）只能省 1%，要省得多得改写技能，每个英雄都要模拟验证，再给用户看。
2. **向开发组反馈**：两处都是引擎内部的复制，修在引擎里所有 mod 都受益：`ModChampionEntry::skill()/skill2()` 每次调用都克隆整个 `DataActionDef`；`prepare_dead_caster_overlay` 对每个施法者已死的投射物每 tick 克隆整个 `Entity`。
3. 定期整体重装：一个英雄一个英雄地装（`--hero`）会让文件又散开。机械盘上隔一段时间用 `--out` 打一份完整的包，像第 1 节那样整个换掉 `mods/league`，冷读取能保持在 4 秒左右。

## 6. 复现方法

1. **每 tick 的 CPU**：`tools/perf/tick.rs` 和平衡模拟器 `sim3.rs` 一样用 mod SDK 编译（把 build.sh 里的文件名换掉），在放着 `sim/assets/` 的文件夹里运行：

   ```bash
   tick.exe 300 1 <蓝方上 野 中 下 辅> <红方上 野 中 下 辅>     # 每个是 .data_champion 路径或 base:<id>
   ```

   第一行的 `cyc_tick_mean` 是每 tick 的平均周期数。`TICK_MODE=view`（默认）是屏幕上的比赛，`plain` 是后台模拟，`sparse` 每 60 tick 才生成一次事件（对局和 view 完全一样，快一倍，还能拿到结算）；`TICK_STATS=1` 打印结算，`TICK_PROJ=1` 列出活了 600 tick 以上的投射物。
2. **热点函数**：编译 tick.rs 时加 `-C link-arg=/MAP:tick.map`，然后 `python tools/perf/profile.py tick.exe tick.map 300 1 <10 个英雄>`，会列出各函数占的样本比例，以及效果树复制是从哪里调用的。
3. **冷读取**：用 `FILE_FLAG_NO_BUFFERING` 打开文件读取，绕过系统缓存；先读几百 MB 别的数据，冲掉硬盘自带的缓存。
4. **引擎行为**：游戏 exe 里的字符串和 Rust 源文件名（`engine-core\src\assets.rs`、`engine-backend-skia\src\platform.rs` 等）可以定位到函数；SDK 的 `libengine_core` rmeta 里能看到 `SoundData { FilePath, BundleRange }`、`RegisterSoundFile` 等类型名。
